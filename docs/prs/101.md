# #101 Erase and Rename

Branch: `101-erase-and-rename`.

## RED

Expected output, error numbers and lines come from `tools/tp5.sh` (TP 5.0 under DOSBox-X);
nothing is hand-written. Probe programs are in `tmp/` (git-ignored); what they showed:

- Erase and Rename act on the file named by `Assign`, whatever its state: an unassigned `Text`
  has an empty name, so both give 2 (not 102 as Reset does); `Assign(f, '')`, `Input` and
  `Output` give 2 as well.
- A file that is open can be erased or renamed (DOS has no sharing here): result 0. An
  erased file stays readable and writable through its open handle and `Close` gives 0; the name
  is gone. A renamed open file keeps reading and writing, and the data lands in the new name.
- Erase of a missing file 2; twice 2. Names are case-insensitive for both arguments.
- Rename: missing source 2; onto an existing name 5 (also onto its own name, in any case);
  empty new name 2; new name with a drive (`A:`) 3; new name with `\` 5. On success the file
  variable's name becomes the new name; on failure it is unchanged.
- Drive-qualified name: Erase 3, Rename (either name) 3.
- With an error already pending, Erase and Rename still run; success leaves the pending
  number, failure replaces it.
- `Rename(f, Chr(66))` and `Rename(f, 'C' + '.TXT')` are accepted (a Char and a string
  expression).
- Compile errors: `Erase;` 88, `Erase(n)` 77, `Erase(f, 5)` 89, `Rename(f)` 87,
  `Rename(f, 5)` 67, `Rename(f, 'X', 'Y')` 89, `Erase('A.TXT')` 20, `Rename(s, ..)` 77,
  `x := Erase(f)` 42.

DOS-only behaviours left untested because the flat host file system cannot match them
(deviation entries to be written with the implementation): wildcards in a name (DOS renames or
erases through them), names longer than 8.3 (DOS truncates silently), DOS device names (decision
50), `NODIR\X.TXT` for Erase (DOS gives 2 or 5 depending on the directory; we give 3, as
Reset does).

### Intended behaviour

`Erase(var f: Text)` and `Rename(var f: Text; newName: String)` in `System`, calling new host
imports `fs_delete(namePtr, nameLen)` and `fs_rename(oldPtr, oldLen, newPtr, newLen)`, each
returning 0 or a negated DOS error. A failure sets `InOutRes` (success leaves it alone) and
Rename changes `f.Name` only on success. `Vfs` gets `delete` and `rename`; a handle follows its
file through rename; Close of an erased file does not resurrect it. A new `onErased(name)` hook
tells the IDE's persistence about deletions and renames (`persist.removeFile`).
