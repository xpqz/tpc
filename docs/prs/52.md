### Intended behaviour

- `uses A, B;` in a program, in a unit's interface and in its implementation. Unit `X` is read
  from the file `X.PAS` (any case) of the registered file table. The native CLI registers the
  `.pas` files of the input's directory, then the files of the directory given with
  `--dir AUXDIR`; a later registration of the same name replaces the earlier (aux wins). Only the
  units a program reaches are lexed and parsed.
- `unit N; interface [uses] decls implementation [uses] decls [begin stmts] end.` Interface
  routine headings are forwards (no `forward` keyword, no body); the implementation defines them
  (parameters may be omitted, 131 if they differ, 59 at the unit's `end` if one is missing).
- Initialisation: the `begin ... end.` part of each unit, in dependency order, before the program
  body; roots for dead-code elimination. `Exit` leaves only that unit's part. `initialization`
  is error 37 (END expected).
- Ordering and cycles (one depth-first walk of `uses`, uses-list order, interface first):
  a unit is initialised after every unit it uses. A unit used while its interface is still being
  read (from an interface or an implementation `uses`) is error 68 at the `uses` entry, reported
  in the file that holds it. A unit used after its interface is complete, even from a unit that
  is itself still open, is fine. Measured on TP 5.0: `Pa` (implementation uses `Pb`) and `Pb`
  (interface uses `Pa`) compile when the program uses `Pa` first (init order Pb, Pa) and are
  `68 5 PA.PAS` when it uses `Pb` first. The brief's "cycles through interfaces" is too coarse:
  the rule is order dependent, and `units.rs` must implement the walk, not a graph property.
  Pinned in both directions.
- Names: a unit's interface names are visible after `uses` and a later `uses` or declaration
  hides an earlier one (unit named last wins). `U.X` (constants, variables, types, routines,
  calls, assignments), `System.X`, and the unit's own name inside it. Names of a used unit's
  `uses` are not re-exported (3).
- Unit name used twice (both `uses` clauses count as one scope), the unit's own name, or `System`
  in a `uses`: error 4 (all measured). A unit without `interface`: 55.
- Errors name their file: `Diag` gains a file index (0 the main program, n the n-th registered
  file); CLI prints `FILE(LINE,COL): Error N: MSG` with the registered base name; wasm
  `err_file()`; `.err` is `N LINE FILE`.
- wasm API: `add_file(name_ptr, name_len, src_ptr, src_len) -> 0|1`. Protocol pinned by
  `tests/wasm_units.mjs` (open question 2).

### Design (for the lead)

- `parse.rs`: `Parser` borrows one shared `Ast` (`&mut Ast`) so units and the program share names
  and nodes. Entry points parse System (a `Kind::Unit` holding all declarations), a unit file and
  the program. New nodes: `Kind::Unit { name, interface_uses, interface, implementation_uses,
  implementation, body }`, `Kind::Program` gains `uses`, `Kind::InitPart(body)` (made by the
  checker). A `uses` clause is a list of `Name` nodes with positions. The parser keeps the unit
  names in scope (System, its own name, names of its `uses`); a unit name followed by `.` and an
  identifier becomes one `Name` with an interned qualified name `U.X` (also in type positions,
  so no change to the type-name slots) and is recorded in `Ast::qualified`. Duplicate names in
  that set are error 4 at the second. Interface routine headings are bodiless routines. A routine
  heading ends at its `;` in an interface part.
- `ast.rs`: `Node` gains `file: u32` (stamped from `Ast::file` by `add`, copied by `typed`), so
  checker diagnostics get their file from the node, and `{$R+}` switches (`RangeSwitch`) are
  per file; positions alone collide across files.
- `symbols.rs`: scope entries are `(name, Sym, imported)`; imports (a `uses`) are entries that do
  not count for the duplicate check, so a declaration may hide an imported name. A registry of
  units `{ name, exports, saved scope }`: System's exports are its whole scope; a unit's
  exports are its own interface entries; `import(name)` pushes a unit's exports; the scope is
  truncated to the System base for each unit. Qualified lookup is inside `lookup` (a name
  registered in `qualified` is looked up in that unit's exports). No `Diag`, no node access.
- `units.rs` (new, Driver component): file table (`add`, find by unit name ignoring case), the
  walk described above (parse a unit when first named; 15 when missing at the `uses` entry, 69
  when the unit's name differs from the requested one, 84 when the file is a program, 68 as
  above), and two lists in `Ast`: units in interface-complete order, units in initialisation
  order. `driver.rs` builds the table (CLI: input directory then `--dir`), stamps each file's
  diagnostics, prints the file name; `ffi.rs` gains `add_file` and `err_file` (the registered
  index is 1 + registration order; the buffer protocol is open question 2); `diag.rs` gains
  `file`, codes 15, 37, 55, 68, 69, 84 and their messages.
- Check order (two phases, because an implementation `uses` may need the interface of a unit
  checked later): System, then each unit's interface in interface-complete order (declare,
  resolve forwards, save the scope and exports), then each unit's implementation in
  initialisation order (restore, import, declare, 59 for an interface heading without a body,
  check the init part), then the program. The program body becomes `Compound[InitPart(b1), ...,
  body]`; codegen gives each `InitPart` its own `block` so `Exit` leaves only that part. The unit
  init parts are therefore DCE roots with no change to the marking.

### Open questions for the lead

1. CLI syntax: `tp5c in.pas -o out.wasm [--dir AUXDIR]` (one directory). The alternative with no
   usage change is the convention `STEM/` beside the input, found automatically (decision 26).
2. `add_file` and `alloc`: `alloc` hands out one buffer valid until the next call, so the test
   protocol is one `alloc` holding the name then the source and `add_file(name_ptr, name_len,
   src_ptr, src_len)` with both ranges inside it (returns 1 otherwise). Files stay registered
   across `compile` calls; the same name (any case) replaces. Alternative: a second buffer.
3. Qualified type names in `var`/parameter positions (`k: Vault.TKey`) cost no checker lines in
   this design but are the decision 33 cut candidate; they have one fixture
   (`qualified_type_names_in_var_and_parameter_positions`) that can be dropped at the verdict.
   The parser mis-reads a record variable named like a used unit (`Point.x`); TP rejects that
   declaration (error 4), so the case is only reachable in nested scopes.
4. `Exit` inside a unit's init part needs the `InitPart` node (about 8 lines); the alternative
   is to leave `Exit` leaving the whole program (a deviation).
5. Prunable at the verdict: `system_in_uses`, `unit_uses_itself`, `unit_in_both_uses_clauses`
   (all error 4 by one rule in the parser), `unit_without_interface_part`.

### Design decisions

- The checker never reads files or orders units; `units.rs` hands it a `Plan`. `symbols.rs` knows nothing of
  files: it keeps exports and saved regions by unit name.
- Interface routine headings are bodiless routines, so the existing forward matching (131, 59) applies unchanged.
- `Exit` in a unit's part is a `block` per `InitPart`; a unit's part is a DCE root because it is part of
  `main` (checked by `unused_unit_routines_are_not_in_the_module`).
- A qualified name is one interned name, resolved in the symbol table, so the checker has no qualified-name code
  and type-name slots stay `u32` (D26 records the one shadowing deviation).
- Not done: `{$I-}` and other file-local switches other than `{$R}` (no such feature yet); the Crt and Dos units
  (a later slice adds their embedded sources to the file table); a unit name declared as a variable in the same
  scope is accepted (TP: error 4), measured and not pinned.
