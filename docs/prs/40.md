### Why each fails today

Pointer syntax is unsupported: `^T` types give error 2 ("Identifier expected"), `New`, `Dispose`, `GetMem`,
`FreeMem`, `Mark`, `Release`, `MemAvail`, `MaxAvail`, `nil`, `@` are unknown (error 3) or `AddrOf` (error 200).
Observed: every program in the lists exits 1 with error 2/3/5/42 at its first pointer construct; every own and
corpus neg program reports a different number than TP5 (mostly 2 or 3); `allocator_is_emitted_only_when_used`,
`pointer_rules_in_the_checker` and the helper test are rejected at the first `^`. The only passing test is the
list-integrity check.

### Intended behaviour

Decisions 12, 18, 21, 25: fixed heap from end of static data to the stack limit, bump allocator plus free list
in `runtime/system.pas`, 203 on exhaustion, 204 for nil, non-heap and wild pointers, double `Dispose` undetected
(D13), `Release` resets the bump pointer and drops free-list entries above the mark, `New`/`Dispose` bound by handle.

### Design decisions

- One helper pair for `New`/`GetMem` and `Dispose`/`FreeMem` (the size is the only difference); no per-type code.
- Heap origin is patched into the data segment rather than computed in Pascal, so the allocator needs no compiler
  intrinsic for "end of static data"; `HeapOrg` and `HeapPtr` must stay adjacent and declared in that order.
- Blocks are multiples of 8, so splitting a free block leaves 0 or at least 8 bytes and `MemAvail` returns exactly
  to its earlier value after a matching `FreeMem`.
- `Dispose` of a block above the bump pointer (for example after `Release`) is 204 here; no corpus program does it.
