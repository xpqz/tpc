## TP5 findings (probed with `tools/tp5.sh`)

- `Val` code: `Integer` or `Word` variable (also an array element, field, `p^`); LongInt, Byte, subrange are 98, a
  literal is 20. The value variable may be Integer, Word, Byte, ShortInt, LongInt or Real; storing is unchecked
  (`65536` into Word is 0, `-1` is 65535, `300` into Byte is 44, `200` into ShortInt is -56).
- Hex literals `$80000000`..`$FFFFFFFF` are the LongInt of that 32-bit pattern (`$FFFFFFFF` is -1,
  `$80000000 - 1` is 2147483647, `$FFFFFFFF div 2` is 0, `$FFFF` stays 65535). Because they are negative, `Word := $FFFFFFFF`
  and `Byte := $FFFFFFFF` are 76, `Integer := $FFFFFFFF` is -1 (accepted). `$100000000` and decimal `2147483648` are 7.
- `LastMode` is a Word variable, 3 at start, assignable. `TextMode(m)` clears the screen, changes the window size
  and sets `LastMode := m`; not cheap, so omitted (D40).
- `SetTextBuf(f, buf[, size])`: `f` a Text variable (77 otherwise), `buf` any variable (20 for a literal), `size` a
  Word expression (38 for Real or Char, 76 for 70000 or -1); one argument is 87, four is 89, as a function 42.

## Design notes

`var_arg` becomes `var_arg_of` (a list of accepted types, `var_arg` calls it with one), so `Val` accepts Integer or Word
code and System's `ValLong` is unchanged (both are 2 bytes, passed by address). `SetTextBuf` is a statement-level intrinsic that emits no code
rather than a System procedure, because the size is optional.
Known quirk not reproduced: TP5 `SetTextBuf` on an open file loses its pending output.
