# #64 Browser tests

Branch: `64-browser-tests`. Tests only: no change to `compiler/src`, `runtime/` or `host/`
(LOC unchanged by this issue: `tools/loc.sh` Host glue 471 / 500, total 8853 / 15000, all from
main). Phase 6 exit tests, run in the installed browsers headless, no downloads, no npm
packages (so no dev-dependency decision to propose).

## How it works

- `tests/host/browser/chrome.mjs`: starts `tools/serve.mjs` (COOP/COEP, so `SharedArrayBuffer`
  works) on a random port and a browser, and gives a test a `page`: `open(wasm)`, `eval`, `key`,
  `click`, `status`, `row`, `until`. Chrome: `--headless=new` driven over the Chrome DevTools
  Protocol with Node 23's built-in `WebSocket`. Firefox 160: `--headless --remote-debugging-port`
  driven over WebDriver BiDi (`session.new`, `script.evaluate`, `input.performActions`, preload
  script); Firefox 160 speaks BiDi on that port without geckodriver. `$BROWSER` selects one.
- Keys are real browser input (CDP `Input.dispatchKeyEvent`, BiDi key actions), so they go
  through the browser's own keydown path into `host/main.js`.
- The page keeps its screen and key queue private, so a preload script wraps
  `Worker.prototype.postMessage` and keeps the `grid` and `keys` SABs the page sends to the
  program Worker (`window.__grid`, `window.__row(n)`). No host change was needed.
- `tests/host/browser/run.mjs`: each test file in each installed browser; Firefox skipped with a
  message if not installed. `make test-browser` runs it. Not part of `make check` (needs a machine
  that can run the browsers).
- Hand-built wasm programs from `tests/host/browser_helpers.mjs` (one helper added:
  `loopEchoProgram`, forever readkey then echo). The wasm files are written to `tmp/browser/`.

## Tests

| File | Checks |
|---|---|
| `stop.mjs` | Spin program (loop that never calls the host). Page timer (20 ms interval) keeps firing while it spins (>= 15 ticks in 500 ms), status "running"; click Stop gives "stopped"; timer still fires after (>= 15 ticks in 500 ms); worst tick gap < 250 ms; Run starts it again and Stop ends it again. |
| `keys.mjs` | Loop echo program. Row 0 is asserted empty first (not vacuous). `a` echoes `a`; Right arrow (ReadKey gives 0 then 77) echoes NUL and `M` (`a M`); `b`; F12 (no ReadKey byte) is swallowed, next `c` echoes (`a Mbc`). |
| `latency.mjs` | 40 keys, 60 ms apart. A page MessageChannel loop polls the cursor byte of the shared grid. Reports key to screen change two ways (below); asserts every key echoed exactly once and in-page worst < 50 ms. |
| `snake.mjs` | Compiles `tests/programs/snake.pas` with tp5c, runs it, checks the score line, the head `O` starts on row 10 and moves right on its own, Down arrow turns it down, `q` ends with "Game over. Score:" and status "finished, exit code 0". **Prints SKIP and passes while `uses Crt` does not compile** (today: `Error 15: File not found` at `(6,6)`; #62 not merged). `SNAKE_STRICT=1` turns the skip into a failure; use it once #62 is on main. |

`tests/programs/snake.pas`: fixed-seed LCG, so the food cells are the same every run. Arrows
(`#0` then 72/80/75/77) or WASD steer, `q` quits. I ran it through the real TP 5.0
(`tools/tp5.sh`): it compiles and draws `Score: 0`. No expected-output oracle is recorded; the test
asserts behaviour on the grid.

## Measurements (this machine, headless, 40 keys)

Chrome (stable, installed):

    end to end  min 2.7  median 10.8  p95 19.2  max 20.7 ms
    in page     min 2.2  median 9.9   p95 18.1  max 20.1 ms
    stop: page timer worst gap 21.9 ms; click Stop to "stopped" 1 ms

Firefox 160:

    end to end  min 0.8  median 1.4  p95 20.5  max 27.2 ms
    in page     min 0.1  median 0.2  p95 8.3   max 8.3 ms
    stop: page timer worst gap 28.9 ms; click Stop to "stopped" 9 ms

"End to end" is from just before the test sends the key (so it includes the protocol round
trip) to the screen byte changing. "In page" is from the page's keydown listener to the change:
the host's own path (ring, `Atomics.notify`, Worker wake, `write`). It excludes the canvas repaint
(next animation frame, up to 16.7 ms more). Both browsers are well under 50 ms. Chrome's in-page
median of about 10 ms is odd against Firefox's 0.2 ms; a probe showed that the time is between the
keydown listener and the Worker consuming the key (the screen changes the same instant), not in
polling (poll gaps under 6 ms). It is probably Worker wake-up scheduling in headless Chrome; not
investigated further. Numbers vary run to run (several runs gave medians 9.6 to 13 ms in Chrome).
